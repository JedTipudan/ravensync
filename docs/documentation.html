1. System Overview
1.1 Purpose of the System

RavenSync is a real-time emergency communication and disaster response management platform designed for educational institutions, barangays, and local communities. It enables administrators and instructors to broadcast emergency alerts instantly, manage communication channels, and monitor the safety status of all users during a crisis.

The platform solves a critical gap in school emergency preparedness — the lack of a centralized, real-time system that works even without internet connectivity. RavenSync operates on a local network (LAN), meaning it functions fully offline as long as the server machine is running, making it ideal for disaster scenarios where internet access is disrupted.

Core Mission: Deliver emergency alerts in under 500ms to all connected users, allow students to report their safety status, and give administrators a live command dashboard to coordinate response — all from a single web application.
Key Capabilities
  • Real-time emergency alert broadcasting via WebSocket and Kafka message broker
  • Student safety status reporting — Safe, Need Help, or Damage Report
  • Interactive campus map with admin evacuation pins and live user location sharing
  • Structured XML data management with DOM/SAX parsing and XSLT transformation
  • Automated PowerShell scripts for backups, health checks, and maintenance
  • Role-based access control — Super Admin, Admin/Instructor, Student
  • Progressive Web App (PWA) — installable on any device, works offline
  • Light and dark mode, fully responsive down to iPhone SE (375px)

DOM: Uses xml2js.Parser with explicitArray:false and mergeAttrs:true. Returns a full JS object convertible to JSON.

SAX: Fires onopentag (element name, attributes, depth), onclosetag, and ontext events. Returns an event log with stats: element count, attribute count, text node count, total events.

4. Technical Explanation
4.1 How Each Requirement Was Implemented

Real-Time Emergency Alerts

When an admin creates an alert via POST /api/alerts, the alertController saves it to MongoDB, then calls publishAlert() from messagingService.js which sends it to the Kafka emergency.alerts topic. Simultaneously, the WebSocket service calls broadcastToAll() sending a NEW_ALERT event to every connected client. The frontend listens with on('NEW_ALERT', ...) and updates the dashboard, shows a toast notification, and triggers the student response panel.

WebSocket Server

Implemented using the ws library in websocketService.js. On connection, the server verifies the JWT token from the query string. Each connected user is stored in a Map keyed by userId. Channel subscriptions are tracked in a separate Map. The server sends a HEARTBEAT every 30 seconds to keep connections alive and detect stale clients.

Kafka Messaging with Offline Fallback

The messagingService.js connects to Kafka on startup. If Kafka is unavailable, all publish calls push to an in-memory offlineQueue array instead. A reconnect timer fires every 10 seconds. When Kafka reconnects, _flushOfflineQueue() drains the array by sending all pending messages. This ensures zero message loss even during broker downtime.

XML Generation

xmlService.js uses xmlbuilder2's fluent API to construct XML documents programmatically. Each generator function (generateAlertsXML, generateUsersXML, generateLogsXML, generateReportXML) builds a document with a namespace declaration, a Summary section, and a data section. Documents are saved to backend/xml/ and also returned via API for live preview.

DOM Parsing Implementation

The parseXML() function wraps xml2js.Parser in a Promise. It uses explicitArray:false so single-child elements are not wrapped in arrays, and mergeAttrs:true so XML attributes are merged into the object alongside child elements. The result is a clean JavaScript object that mirrors the XML structure.

SAX Parsing Implementation

The saxParseXML() function creates a sax.parser in strict mode with trim and normalize options. It tracks depth as a counter incremented on openTag and decremented on closeTag. All events are pushed to an events array. The parser returns both the full event log and a statistics summary, making it useful for XML structure analysis and validation.

XSLT Transformation

The transformXML() function checks the requested format. For JSON, it calls parseXML() and serializes the result. For HTML, it calls parseXML() then passes the object to generateHTMLReport() which detects the document type (alerts, users, logs, report) and builds a styled HTML page with a header, stat cards grid, and a data table. The XSL file provides an alternative pure-XSLT path for the emergency alerts report specifically.

Campus Map with Offline Support

The map uses the school's actual PNG image served as a static file. Zoom and pan are implemented with CSS transform: translate() scale() on a wrapper div — no map library needed. Admin pins are saved to MongoDB via POST /api/map/admin-pins and loaded on page mount. User location pins are sent via WebSocket LOCATION_SHARE and also saved to MongoDB via POST /api/map/pins so they survive admin page refreshes. The map works fully offline on LAN.

Role-Based Access Control

The protect middleware verifies the JWT Bearer token on every API request. The authorize(...roles) middleware checks req.user.role against the allowed roles array. Three roles exist: superadmin (full access), admin (instructor-level), and user (student). The frontend also checks roles before rendering admin-only UI elements using the isAdmin() helper from auth.js.

PWA and Offline Caching

sw.js registers a Service Worker that caches static assets (HTML, CSS, JS, images, fonts) on install. On fetch, it uses a cache-first strategy for static files and network-first for API calls. The web manifest enables Add to Home Screen on mobile and desktop. The app is fully installable and shows cached content when offline.

Security Implementation

  • Helmet sets 11 HTTP security headers including X-Frame-Options, X-Content-Type-Options, and Referrer-Policy
  • express-rate-limit restricts API to 100 requests per 15 minutes per IP in production
  • express-mongo-sanitize strips $ and . from request bodies to prevent NoSQL injection
  • bcryptjs hashes passwords with 12 salt rounds — computationally expensive to brute-force
  • JWT tokens expire after 7 days. Invalid or expired tokens trigger auto-logout on the frontend
  • All admin actions are logged to the AuditLog collection with user, action, resource, and IP address
4.2 Challenges Encountered and Solutions
ChallengeSolution
Kafka container keeps stopping in Docker Added restart:always policy, changed ADVERTISED_LISTENERS from localhost to host.docker.internal (Windows Docker), capped heap with KAFKA_HEAP_OPTS: -Xmx512m -Xms256m to prevent OOM kills
Map pins lost on admin page refresh Admin pins moved from localStorage to MongoDB (AdminPin model). User location pins also persisted to MongoDB (LocationPin model) via both WebSocket handler and REST API call simultaneously
Channels page unusable on mobile — side-by-side layout too narrow Implemented mobile-first panel switching: channel list is full-screen on mobile, tapping a channel hides the list and shows full-screen chat. Back arrow returns to list. Desktop layout unchanged
Message action buttons (reply/edit/delete) not accessible on mobile — hover-only Added visible pill buttons below each message on mobile (sm:hidden), kept hover overlay on desktop (hidden sm:flex)
Sidebar overflows on short screens with 10 nav items Changed sidebar to height:100vh with overflow:hidden. Nav section gets flex:1 and overflow-y:auto so it scrolls independently while header and footer stay pinned
Dark mode text invisible on landing page Replaced all var(--text-secondary) with var(--text-primary) + opacity:0.75 so text is always readable on both themes. Secondary color was too dark on dark backgrounds
Kafka ADVERTISED_LISTENERS misconfigured Changed from PLAINTEXT://localhost:9092 to PLAINTEXT://host.docker.internal:9092 so Node.js running outside Docker can reach the broker correctly on Windows
User management table unreadable on mobile Added a parallel mobile card list (sm:hidden) that renders each user as a compact card. Desktop table hidden on mobile (hidden sm:block). Both populated from the same loadUsers() function
